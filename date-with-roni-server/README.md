# date-with-roni-server

צד השרת של הדייט, ב-Kotlin עם Ktor, רץ בדוקר.

**זה API של JSON ותו לא.** הוא לא מגיש HTML, לא נכסים סטטיים ולא דפי שגיאה —
כולל ה-404 וה-500, שגם הם JSON. הפרונט הוא image נפרד עם עולם משלו.

כרגע זה השלד: מאזין, עונה, מוכן לקונטיינר.

## הרצה בדוקר

```bash
docker compose up --build
```

```bash
curl http://127.0.0.1:8080/api/health
```

## פיתוח מקומי

השרת רץ אצלך, ה-DB עונה מהשרת. אין דוקר מקומי ואין דיבאג בפרודקשן.

**חלון אחד — המנהרה:**

```bash
./dev-tunnel.sh
```

מעבירה את `localhost:5432` שלך אל ה-Postgres שבשרת, דרך SSH. ה-DB עצמו
נשאר בלי פורט מפורסם ובלי גישה מהאינטרנט — המנהרה עוברת בחיבור המוצפן שלך
בלבד, ורק אל 127.0.0.1 של המחשב הזה. השאר את החלון פתוח.

**חלון שני — השרת:**

```bash
JAVA_HOME=$HOME/.jdks/openjdk-26.0.1 ./gradlew run
curl -s http://127.0.0.1:8080/api/health
```

`./gradlew run` טוען את `.env` לבד, אז אין `export` ידני. צריך למלא שם
`DATABASE_PASSWORD` — הסיסמה מתוך ה-`.env` שעל השרת.

`"db":"up"` בתשובה אומר שהכל מחובר.

### אם משהו לא עובד

| מה שרואים | מה זה |
|---|---|
| `אין DATABASE_URL` | ה-`.env` לא נמצא או ריק |
| `password authentication failed` | הסיסמה ב-`.env` לא תואמת לזו שבשרת |
| `Connection refused` | המנהרה לא פתוחה |
| `bind: Address already in use` | מנהרה או Postgres אחר כבר תפסו את 5432 |

`ExitOnForwardFailure=yes` בסקריפט קיים בשביל השורה האחרונה: בלעדיו ssh
מתחבר בהצלחה **בלי** ההעברה, ואתה מקבל מנהרה שנראית פתוחה ולא מעבירה כלום.

### הסכימה

ה-DB שבשרת עדיין בלי טבלאות. מריצים את ה-SQL דרך DataGrip, שכבר מחובר
דרך אותה מנהרה.

## מה יש כאן

| נתיב | תשובה |
|------|--------|
| `POST /api/login` | `{credential}` → `{token, email, name, tokensSpent}` |
| `GET /api/health` | `{"ok":true,...,"db":"up"}` — `db` הוא `up` / `down` / `not-configured` |
| כל השאר | `404` עם `{"error":"אין נתיב כזה."}` |

שני משתני סביבה: `HOST` (ברירת מחדל `0.0.0.0`) ו-`PORT` (ברירת מחדל `8080`).

## שתי החלטות שכדאי לדעת עליהן

**השרת מאזין על `0.0.0.0`.** בתוך קונטיינר, האזנה על `127.0.0.1` אומרת ששום
דבר מחוץ לקונטיינר לא מגיע אליו — גם לא קונטיינר אחר באותה רשת. הבידוד נעשה
שכבה אחת מעל: ב-`docker-compose.yml` הפורט מפורסם כ-`127.0.0.1:8080:8080`,
כלומר נגיש רק מהמארח עצמו ולא מהאינטרנט.

**קונטיינר הפרונט לא צריך את הפורט המפורסם הזה בכלל.** שניהם על הרשת
`date-with-roni`, אז הוא פונה ישירות ל-`http://api:8080`. הפרסום למארח הוא רק
בשביל `curl` מהירים בזמן פיתוח.

## הרשת

```
                        ┌─────────────────────┐
     :80/:443 ──────────│  nginx / web        │
                        │  (image נפרד)       │
                        └──────────┬──────────┘
                                   │  http://api:8080
                        ┌──────────┴──────────┐
      רשת: date-with-roni             api     │  JSON בלבד
                        └──────────┬──────────┘
                                   │  db:5432
                        ┌──────────┴──────────┐
   רשת: date-with-roni-backend        db      │  postgres 18
        internal: true    └─────────────────────┘   בלי ports
```

**nginx לא מדבר עם ה-DB, ולא צריך.** Postgres מדבר בפרוטוקול בינארי משלו על
TCP, לא HTTP. ל-nginx יש מודול `stream` שיודע להעביר TCP גולמי, אבל להשתמש בו
כאן זה בדיוק לפתוח את ה-DB לעולם. השרשרת היא עולם → nginx → api → db, ו-nginx
בכלל לא יודע שה-DB קיים.

שתי שכבות מפרידות בין ה-DB לאינטרנט:

1. **אין `ports`** בשירות ה-db. שום פורט לא מפורסם למארח, אז אין דרך להגיע
   אליו מבחוץ. זו השורה הכי חשובה בקובץ — והיא שורה שלא קיימת.
2. **`internal: true`** על רשת `date-with-roni-backend`. לרשת הזו אין שער
   יציאה, אז גם אם מישהו יריץ קוד בתוך קונטיינר ה-DB — אין לו לאן לצאת.

ה-api יושב על שתי הרשתות, ולכן מדבר גם עם ה-db וגם עם העולם (הוא צריך את
זה בשביל ה-API של Anthropic).

## Postgres

`postgres:18-alpine`. הדאטה נשמר ב-volume בשם `date-with-roni-pgdata`.

### מלכודת שכדאי להכיר

**ב-Postgres 18 השתנה מיקום הדאטה.** עד 17 היה `PGDATA=/var/lib/postgresql/data`,
ומ-18 זה `/var/lib/postgresql/18/docker`, כשה-volume עצמו עבר ל-`/var/lib/postgresql`.

כמעט כל מדריך, ורוב תבניות ה-Stack המוכנות, עדיין כותבים
`- pgdata:/var/lib/postgresql/data`. עם image של 18 זה **לא ייכשל** — הוא פשוט
יעלה, יעבוד, וישמור את הדאטה בשכבת הכתיבה של הקונטיינר במקום ב-volume.
הכל ייראה תקין עד ה-`docker compose down` הראשון, ואז הדאטה ייעלם.

בקובץ כאן זה `- pgdata:/var/lib/postgresql`. אם אתה מעתיק תצורה ממקום אחר —
זו השורה לבדוק.

### הרצה

```bash
cp .env.example .env
openssl rand -base64 32      # להדביק לתוך POSTGRES_PASSWORD
docker compose up -d --build
```

### להתחבר ל-DB

מהשרת עצמו:

```bash
docker exec -it date-with-roni-db psql -U dateroni -d dateroni
```

ב-Portainer: Containers → `date-with-roni-db` → Console → `/bin/sh`, ואז אותה
פקודת `psql`.

מכל מקום, בלי להיכנס לקונטיינר ה-DB — קונטיינר חד-פעמי על הרשת הפנימית:

```bash
docker run --rm -it --network date-with-roni-backend \
    postgres:18-alpine psql -h db -U dateroni -d dateroni
```

**מכלי גרפי במחשב שלך** אין דרך ישירה, וזה מכוון — הפורט לא מפורסם, והרשת
`internal`. שתי אפשרויות אם באמת צריך: להוסיף זמנית `-p 127.0.0.1:5432:5432`
ולפתוח מנהרת SSH (`ssh -L 5432:127.0.0.1:5432 ubuntu@<server-ip>`), ולהחזיר
לקדמותו אחרי; או להרים pgAdmin כשירות נוסף על `backend` ולגשת אליו דרך nginx.
לרוב `psql` דרך Portainer פשוט יותר משתיהן.

### סכימה

`migrations/002-google-login.sql` — להריץ ב-DataGrip.

הטבלה `chicks`: שורה אחת לאדם, מייל כמפתח ראשי. מייל, שם, `google_sub`,
hash של טוקן הסשן, האם הסשן פעיל, כמה טוקנים נשרפו, האם קיבלה את הוואטסאפ,
והאם קבעה דייט (מתי ואיפה).

`google_sub` הוא המזהה היציב של חשבון גוגל. כתובת מייל *כן* יכולה להשתנות
בחשבון; `sub` לעולם לא.

**מה שאין בה, ובכוונה:** תוכן ההודעות ושום סיכום שלהן. הטבלה יודעת *שהייתה*
שיחה ומה יצא ממנה — לא על מה דיברו.

## בריכת החיבורים

`Database.kt`. HikariCP מעל דרייבר ה-JDBC של Postgres — Ktor לא מביא בריכה
משלו, ו-Hikari היא ברירת המחדל בעולם ה-JVM.

נפתחת פעם אחת לכל חיי התהליך ונסגרת ב-`ApplicationStopped`. שלוש נקודות
שכדאי להכיר:

**כל גישה ל-DB עוברת דרך `Dispatchers.IO`.** JDBC הוא API חוסם, והמסלולים
ב-Ktor רצים על התהליכונים של Netty, שמספרם קטן. שאילתה שנחסמת על אחד מהם
משביתה אותו לכל הבקשות האחרות, וכמה שאילתות איטיות במקביל משתקות את השרת
כולו. `Database.query { }` עוטף את זה, וזו הסיבה שהוא `suspend`.

**חמישה חיבורים, לא חמישים.** בריכות קטנות מהירות יותר מגדולות — זו ההמלצה
של Hikari עצמה. כל חיבור הוא תהליך בצד Postgres, ויותר חיבורים מקבילים
מליבות פנויות רק מוסיפים החלפות הקשר. `DB_POOL_SIZE` משנה את זה.

**נכשלת מיד אם אין חיבור.** עדיף שהקונטיינר ייפול על הגדרה שגויה מאשר יעלה
ויחזיר 500 לכל בקשה. ב-compose יש `depends_on: service_healthy`, אז ה-DB
כבר מוכן בשלב הזה. בלי `DATABASE_URL` בכלל השרת עולה בלי DB — כדי שאפשר
יהיה להריץ מקומית בלי Postgres.

### משתני סביבה

| | |
|---|---|
| `DATABASE_URL` | `jdbc:postgresql://db:5432/dateroni` |
| `DATABASE_USER`, `DATABASE_PASSWORD` | מ-`.env` |
| `DB_POOL_SIZE` | ברירת מחדל 5 |

## מבנה

## כניסה עם גוגל

אין הרשמה, אין קוד במייל, אין אקטיבציה. גוגל כבר הוכיחה שהכתובת שלה —
אין טעם לעשות את זה פעם שנייה.

```
דפדפן                              שרת                      גוגל
  │  כפתור "התחבר עם גוגל"          │                         │
  │─────────────────────────────────────────────────────────▶ │
  │ ◀──────────── ID token (JWT) ─────────────────────────────│
  │  POST /api/login {credential}   │                         │
  │────────────────────────────────▶│  מאמת חתימה מול         │
  │                                 │  המפתחות של גוגל ──────▶│
  │ ◀───── טוקן סשן משלנו ──────────│                         │
```

זה **לא** ה-OAuth עם ההפניות: אין client secret, אין redirect, אין refresh
token. רק ID token שנבדק פעם אחת.

**הטוקן של גוגל משמש רק בכניסה.** מכאן הדפדפן מחזיק טוקן סשן משלנו — הטוקן
של גוגל פג אחרי כשעה, והסשן שלנו נושא מצב משלו (תקציב, תפוגה).

### מה שהאימות בודק

| | |
|---|---|
| חתימה | מול המפתחות הציבוריים של גוגל |
| `aud` | שהטוקן הונפק ל-Client ID **שלנו** |
| `exp` | שלא פג |

הבדיקה האמצעית היא הלא-מובנת-מאליה. בלעדיה אפשר להביא ID token תקף לגמרי,
שגוגל הנפיקה לאתר אחר, ולהיכנס איתו לכאן.

ולעולם לא לקרוא את תוכן ה-JWT לפני אימות החתימה — JWT הוא base64, לא
הצפנה. כל אחד יכול לכתוב אחד ולטעון בו שהוא כל כתובת שירצה.

### הגדרה ב-Google Cloud

1. [console.cloud.google.com](https://console.cloud.google.com) → פרויקט חדש
2. APIs & Services → OAuth consent screen → External
3. Credentials → Create credentials → OAuth client ID → **Web application**
4. Authorized JavaScript origins:
   `https://date-with-roni.com` וגם `http://localhost:5173` לפיתוח
5. את ה-Client ID ל-`GOOGLE_CLIENT_ID` ב-`.env`

**Client secret לא נדרש** בזרימה הזו.

| | |
|---|---|
| `DATABASE_URL` | `jdbc:postgresql://db:5432/dateroni` |
| `DATABASE_USER`, `DATABASE_PASSWORD` | מ-`.env` |
| `DB_POOL_SIZE` | ברירת מחדל 5 |

## מבנה

```
Dockerfile                             בנייה דו-שלבית, רץ כלא-root
docker-compose.yml                     api + db, שתי רשתות
dev-tunnel.sh                          מנהרת SSH ל-DB שבשרת
.env.example                           הסיסמה של ה-DB
build.gradle.kts                       תלויות ובנייה
src/main/kotlin/com/dateroni/
  Application.kt                       ← השרת
  GoogleAuth.kt                        אימות ה-ID token
  Chicks.kt                            גישה לטבלה
  Tokens.kt                            יצירת סודות וגיבוב
  Database.kt                          בריכת החיבורים
migrations/                            SQL להרצה ידנית
src/main/resources/logback.xml         לוגים
```

## מה הלאה

השרת ב-Node שב-`date-with-roni-website/server/` נשאר בדיוק כמו שהוא, עובד,
ומשמש כרפרנס. בונים כאן מול אותו חוזה API, לפי הסדר:

1. סשנים בזיכרון — טוקן, קוד אקטיבציה, תפוגה, תקציב.
2. נקודות הקצה של החוזה.
3. שליחת מייל.
4. הסוכן, עם ה-SDK הרשמי של Anthropic לג'אווה (`com.anthropic:anthropic-java`).

### הערה על `/activate`

בגרסת ה-Node, הקישור מהמייל מוביל ל-`GET /activate` שמחזיר **דף HTML**
("אישרנו אותך, אפשר לחזור ללשונית"). כאן זה לא יכול לגור — אין HTML בשרת הזה.

הקישור במייל יצטרך להצביע על קונטיינר הפרונט, והוא זה שיקרא ל-API כדי לבצע
את האקטיבציה בפועל. זה אומר שהחוזה משתנה בנקודה הזו: במקום `GET /activate`
שמגיש דף, תהיה נקודת קצה כמו `POST /api/activate` שמקבלת את הקוד ומחזירה JSON.
נסגור את זה כשנגיע לאקטיבציה.
